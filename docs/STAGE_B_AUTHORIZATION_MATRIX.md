# Stage B authorization matrix and code-path audit

**Audit date:** 2026-11-01
**Branch:** `arena/042d6599-videl0` (PR #5; must remain open/unmerged)
**Boundary:** source and offline-test review of authorization-relevant bot, connected-DM, Group Manager/Studio, owner, and web API paths. Telegram, production MongoDB, staging, and real browser/device behavior were not exercised. This is not a claim that unrelated application logic or deployment behavior has been exhaustively proven.

## Authorization invariants

1. A connected-group target is read from the server-side connection for the authenticated Telegram actor. A callback's chat/group identifier is checked against that connection; it never selects an arbitrary target. The private interaction chat and target group remain distinct.
2. Group mutations re-check current Telegram group-admin status at callback/reply/commit boundaries. A global owner exception in the legacy `is_user_authorized` helper is distinct from sudo; sudo does not itself grant group-admin authority. Web Group Manager paths require the signed Telegram actor to be a current admin. The owner-only Group View has a separate owner gate and does not make its owner-only controls available to group admins.
3. Bot rights are method-specific and checked before the corresponding Telegram mutation or before enabling a protection that depends on that right. A current caller role does not imply the bot has the needed rights.
4. Settings writes use the existing `mgmt_chat_settings.revision` CAS path where the caller presents a revision. Volatile drafts do not write until confirmation. Listening-session creation uses its existing collection and an idempotency key; filter mutations use the existing duplicate-safe lease/snapshot helper.
5. Cancellation and expiry discard a draft. Telegram/DB errors do not become success-shaped responses. Where an external operation can have ambiguous delivery, code reports uncertainty instead of blind retry.

### Interaction lifecycle / failure coverage

The reusable `videl/utils/interactive_settings.py` engine binds session token to interaction chat, actor, and target; binds replies and previews to exact message IDs; expires volatile drafts; supports cancel/edit; and claims commit single-flight before invoking a fresh authorization callback and saver. Failed auth/save returns to preview; successful save consumes the session. This audit added a no-input `begin_preview()` constructor that reuses those guarantees for explicit confirmation workflows; it is used for approved-list clearing, not a second session store.

Focused regression tests now cover multiple connected editors' authorization revocation, actor/target isolation, stale revisions, timeouts, cancellation, duplicate confirmation, rights loss and persistence failures. Exact matrix coverage varies by editor; tests are mocks and do not establish live Telegram, Mongo, or cross-process behavior. Process-local interaction sessions are intentionally lost on restart without mutating stored configuration.

## Web authorization and route inventory

`webapp/src/lib/auth.ts` defines an expiring signed owner cookie bound to `OWNER_ID`, secret-prefix HMAC validation, timing-safe comparison, and cross-site state-change rejection. `player-auth.ts` uses a separate cookie name, signing prefix, TTL and actor assertion; owner cookies do not satisfy player guards and vice versa. Group Manager backend routes validate short-lived actor assertions and re-check Telegram admin status on each request. State-changing owner/player routes reject cross-site requests. The repository's `api-auth-inventory.test.ts` verifies every API route declares an owner/player guard or a documented public-auth boundary. Route coverage (49 handler files):

- **Owner-only (`ownerRequired`)**: `/api/analytics`, `/api/bot-settings`, `/api/broadcast`, `/api/channel`, `/api/chat`, `/api/chat-photo`, `/api/conversations`, `/api/federation`, `/api/federation/[id]`, `/api/group-view`, `/api/groups`, `/api/groups/[id]`, `/api/groups/[id]/audit`, `/api/groups/[id]/backup`, `/api/groups/bulk`, `/api/health`, `/api/inbox-media`, `/api/inbox-workspace`, `/api/music/search`, `/api/music/status`, `/api/music/track/[videoId]`, `/api/onboarding`, `/api/ops/events`, `/api/ops/logs`, `/api/ops/metrics`, `/api/ops/music`, `/api/ops/protection`, `/api/premium-emoji`, `/api/schedules`, `/api/schedules/duplicate`, `/api/schedules/retry`, `/api/schedules/series`, `/api/stats`, `/api/summary`, `/api/version`.
- **Telegram-player (`playerRequired`)**: `/api/arcade`, `/api/arcade/avatar/[id]`, `/api/arcade/clip/[id]`, `/api/arcade/events`, `/api/arcade/events/[id]`, `/api/arcade/events/groups`, `/api/arcade/join`, `/api/arcade/player/[id]`, `/api/arcade/profile`, `/api/arcade/room/[code]`, `/api/manager`, `/api/manager/[id]`.
- **Explicit auth/session boundaries**: `/api/auth` verifies owner Telegram login and checks the configured owner ID before minting the owner cookie; `/api/session` verifies Telegram identity and manages the separate player cookie. These two routes do not rely on an already-issued cookie for login/logout operations and apply cross-site checks on state changes.

### Web trust and revocation caveat

Owner/player cookies are stateless signed bearer tokens. Logout clears the browser's cookies but cannot invalidate a copied token server-side; expiry or signing-secret rotation invalidates it. Telegram group-admin membership is rechecked by Group Manager backend requests, so a previously issued player cookie alone does not preserve group-admin powers. A general immediate per-token web-session revocation ledger is not present; treat this as an open security/session-management follow-up, not as verified revocation. This audit did not add a parallel session store.

## Owner, sudo, and boundary checks

- Owner-only browser operations use `ownerRequired`; player routes use the distinct `playerRequired`; cross-cookie tests deny owner sessions at player routes and player sessions at owner routes.
- Group Manager actor identity is a signed Telegram user ID with a short expiry, not a user ID trusted from the JSON body. Backend admin checks are current. Private group-view actions require an owner-authenticated proxy and owner-only actions remain unavailable in Group Manager scope.
- `videl/utils/permissions.py` documents the configured global owner as a trusted exception to group-admin command authorization. This exception is not a sudo-user rule. Sudo controls live in explicit owner/sudo command surfaces; they do not change `connected_target()` or `manager.require_admin()` outcomes. Review the action's intended owner-vs-group-admin policy before expanding any exception.
- Bot admin privileges do not establish caller authorization; caller role and bot operation rights are separate checks.

Regression tests cover auth revocation, stale list, target scope, success and duplicate confirmation.

6. **Still open:** stateless owner/player session cookies have no immediate server-side token revocation; logout clears the current browser only. Avoid adding a second auth/session system; evaluate with the existing security roadmap.
