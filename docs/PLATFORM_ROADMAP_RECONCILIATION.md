# Platform roadmap reconciliation against the active Videl worktree

**Purpose:** reconcile the proposed platform roadmap with existing Videl behavior before adding another feature. This is a source-level review of the current worktree, not a fresh full test run or a production audit. It follows `todo.md`'s rule: candidate ideas are not proof of missing capability; re-check code and avoid duplicate surfaces.

## Executive summary

Several proposed areas already have substantial implementations and should be improved in place, not recreated:

- Group health and setup already exist in the Group Manager (`videl/utils/group_health.py`, `videl/utils/group_view.py`, `webapp/src/components/studio/screens/Groups.tsx`, and `AdminGroups.tsx`). The health score is an explainable checklist/sorting aid based on configured protection, Telegram availability/admin status and recorded inbox counts; it is not a measured overall community-engagement score.
- Command analytics, group rankings, onboarding verification aggregates, service health and operations signals already exist (`videl/utils/analytics_privacy.py`, `videl/utils/onboarding.py`, `OwnerHome.tsx`, `Analytics.tsx`, `/api/health`, and `/api/ops/*`). Missing member-return/retention trends and weekly group-health narratives are real gaps, but data collection and privacy requirements must be specified first.
- Moderation records and review surfaces already span reports, appeals, warnings, join requests, escalations, notes, audit history and member case timelines. A new collection-centric “case center” would duplicate those stores. The verified gap is cross-source navigation/state/assignment, not lack of moderation records. This continuation adds an explicit completeness status for the six existing case-history sources; the timeline now distinguishes complete-empty from partial/unavailable reads instead of silently presenting query failures as “no activity.”
- Guided setup, permission diagnostics and group setup checklists already exist in the Admin Group view and group detail. Improve that flow rather than create a second wizard.
- Scheduled posts are already a persistent Mongo-backed queue with atomic claims, bounded retries for explicit Telegram rate limits, cancellation/retry, recurrence and status. A durable generic job registry and resumable broadcast delivery are not the same feature and remain gaps.
- Group music controls already exist separately from the browser music player; `/api/ops/music` is owner-only aggregate telemetry, not a group playback controller. Inspect the existing Group Manager/music handoff before expanding it.
- The Settings screen provides Videl app health, release compatibility and diagnostics, but explicitly does not show Render deployment history/build logs/platform metrics. A genuine Render control-plane integration is therefore missing, not a UI relabeling task.

## Release/security prerequisites and constraints

The proposal references credential revocation (#234), staging/recovery validation (#248), exact deployment revisions, and authorization checks. Those are not all source-only tasks. Do not claim completion from mocks or this review. Credential rotation, production-copy remediation, staging use, live Telegram delivery, Render/Vercel inspection, production DB changes, merge, push, or deployment require the existing user coordination/authorization constraints and appropriate connected environments. This document does not access credentials or external services.

The worktree is already broadly dirty (188 paths reported modified/untracked at review start), including ongoing Playeon-inspired work and the initial shared-listening-room backend/API foundation. Preserve all of it; no reset, clean, rebase, commit, push, merge or deployment was performed for this reconciliation.

## Recommended next sequence

1. Keep the `todo.md` active audit as the execution authority; do not promote every idea in this proposal to an implementation task.
2. Finish route/store tests and the separate shared-listening-room UI work already in progress, unless the user explicitly reprioritizes to the platform roadmap.
3. For the platform roadmap, the highest-value local/source-safe task is a focused moderation-case workflow gap audit using the existing report/appeal/warning/audit stores. Group Intelligence should follow only with a privacy-reviewed data contract. A Render integration should wait until a read-only API contract and privately configured credential are available.
4. Re-run the relevant offline Python/web tests and static checks after implementation. State clearly which live, device, staging and production validations did not occur.
